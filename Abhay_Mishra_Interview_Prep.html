What is SOA (Service-Oriented Architecture)? How is it different from Microservices?

SOA (Service-Oriented Architecture) is an architectural approach where large business functions are built as reusable services. These services communicate through a central component called the Enterprise Service Bus (ESB). The ESB acts like a central hub—it routes requests, transforms message formats, handles security, logging, and connects different enterprise systems, so individual services don’t need to communicate directly with each other.

Microservices follow a different approach. Instead of large shared services, the application is divided into small, independent services. Each service has its own business responsibility, its own database (where possible), and can be developed, deployed, and scaled independently. These services usually communicate using lightweight APIs like REST or asynchronous messaging platforms like Kafka.

In the banking industry, both architectures are commonly used together. Core banking and legacy systems are often built using SOA with an ESB because they need to integrate many enterprise applications reliably. On the other hand, modern digital platforms such as mobile banking, chatbots, notification systems, and campaign engines are generally built using microservices for better scalability and faster development.

In my SBI Card project, I worked on a microservices-based campaign platform where services communicated through Kafka for real-time event processing. At the same time, this platform integrated with existing enterprise systems that followed SOA principles. So, I have experience working in an environment where SOA and microservices coexisted and complemented each other.

Q3. Explain Apache Kafka and how you’ve used it

Apache Kafka is a distributed event streaming platform used to exchange data between applications in a fast, reliable, and scalable way. It allows applications to communicate asynchronously, so they don’t have to wait for each other.

How I used Kafka at SBI Card

At SBI Card, I worked on a Kafka-based campaign engine for customer lead retargeting.

The flow was:

  • Customer performs an action (e.g., abandons card application)
  • Our application creates a campaign event
  • The event is published to a Kafka Topic

Multiple services consume the same event independently:

  • Email Service sends an email
  • SMS Service sends an SMS
  • Call Center Service creates a calling task
  • Reporting Service updates reports

If one service fails, the others continue processing, making the system highly reliable.

Why Kafka instead of RabbitMQ?

Kafka is better for high-volume event streaming, scalability, and replaying messages, while RabbitMQ is better for traditional message queues.

What is a Partition?

A Partition divides a Kafka Topic into multiple parts so messages can be processed in parallel.

How does Kafka maintain message ordering?

Kafka guarantees message ordering only within a single partition.

What is a Consumer Group?

A Consumer Group is a set of consumers that share the processing of messages from a Topic.

What is an Offset?

An Offset is the unique sequential number of every message within a partition

What happens if a Broker goes down?

Kafka automatically switches to a replica broker, so message processing continues without interruption.

What is Replication?

Replication means keeping multiple copies of data on different brokers for fault tolerance and high availability.

What is a Dead Letter Queue (DLQ)?

A DLQ stores messages that fail processing even after multiple retry attempts.

How do you avoid duplicate message processing?

By using idempotent processing, unique message IDs, and committing offsets only after successful processing.

What is Idempotency?

Idempotency means processing the same message multiple times still produces the same result only once.

What monitoring tools did you use for Kafka?

Kafka UI, Prometheus, Grafana, application logs, and JMX metrics are commonly used to monitor Kafka.

How would you increase Kafka throughput?

Increase partitions, add more brokers, optimize batch size, compression, and consumer parallelism

How many partitions should a Topic have?

It depends on the expected traffic and required parallel processing, with at least as many partitions as concurrent consumers.

What happens when the number of consumers is greater than the number of partitions?

Extra consumers remain idle because one partition can be consumed by only one consumer within a consumer group.

  • Code changes

  • Deployment

With Drools:

  • Developers didn’t need to modify application code for every business change.

Microservices

  1. API Gateway
  • What it is: The single main door for all client requests entering your microservice system.
  • Why we use it: Instead of web/mobile apps calling 20 different microservices directly, they call the Gateway. It handles routing, security checks, and rate-limiting in one central place.
  • Interview Answer: “We used Spring Cloud Gateway as our single-entry point. It handled routing, JWT token validation, and rate-limiting before requests hit our microservices. This kept our internal services secure and simplified our frontend integration.”
  1. Service Discovery (Eureka)
  • What it is: A dynamic address book for your microservices.
  • Why we use it: Microservices constantly start, stop, or move across servers with changing IP addresses. Eureka keeps track of where every healthy service is currently running.
  • Interview Answer: “We used Netflix Eureka so microservices could find each other automatically. When a service started up, it registered its IP with Eureka, allowing other services to call it dynamically without hardcoded URLs.”
  1. Config Server
  • What it is: A single central store for all application configurations and properties.
  • Why we use it: Storing settings inside each service makes changes painful. Config Server lets you manage properties for Dev, QA, and Prod in one central Git repository.
  • Interview Answer: “We used Spring Cloud Config Server backed by Git to manage application properties centrally. This allowed us to update configurations across environments without re-building microservice code.”
  1. Circuit Breaker (Resilience4J)
  • What it is: An automatic safety switch that stops calling a failing service.
  • Why we use it: If a third-party API is failing or slow, continuously calling it hangs your system. A Circuit Breaker temporarily stops requests and returns a quick fallback answer instead.
  • Interview Answer: “We used Resilience4J Circuit Breaker for external vendor APIs. If vendor failures spiked, the circuit opened, preventing system slowdowns and returning a fallback response until the vendor recovered.”
  1. Retry Pattern
  • What it is: Automatically trying a failed request again after a short pause.
  • Why we use it: Some errors are just temporary network hiccups. Retrying with a small delay (and randomized backoff) helps recover without failing the user request.
  • Interview Answer: “We configured retries with exponential backoff for temporary network errors. This automatically recovered transient failures without overloading downstream systems with simultaneous retries.”
  1. Timeout
  • What it is: Setting a maximum wait time for a service response.
  • Why we use it: Prevents a service from waiting forever on a slow dependency, which frees up system resources to handle other incoming users.
  • Interview Answer: “We configured strict timeouts on all external API calls. If a service didn’t respond within 2 seconds, the request failed quickly so user threads weren’t left hanging indefinitely.”
  1. Idempotency
  • What it is: Ensuring duplicate requests produce the exact same result as a single request.
  • Why we use it: If a user clicks ‘Pay’ twice or a network retry sends the same payment twice, idempotency prevents double billing or duplicate records.
  • Interview Answer: “Every payment request included a unique Transaction ID. We checked this ID in Redis before processing, ensuring retries never created duplicate transactions.”
  1. Saga Pattern
  • What it is: Managing multi-service workflows without using single database transactions.
  • Why we use it: Since each service has its own database, a failure in Step 3 requires running “compensating actions” to undo Step 1 and Step 2.
  • Interview Answer: “We used the Saga pattern for distributed workflows like onboarding. Each service completed its local transaction, and if a later step failed, compensating events reversed the earlier steps.”
  1. Event-Driven Architecture (Kafka)
  • What it is: Services communicating asynchronously by publishing and consuming events.
  • Why we use it: Instead of Service A waiting on Service B, Service A publishes a message to Kafka and moves on. Other services process that message independently.
  • Interview Answer: “We built an event-driven flow using Kafka. When a customer completed an order, we published an event, allowing Email, SMS, and Analytics services to process it independently.”
  1. Database per Service
  • What it is: Giving every microservice its own dedicated database.
  • Why we use it: Prevents services from sharing tables. This keeps services loosely coupled so changes in one database don’t break other services.
  • Interview Answer: “Every microservice managed its own database and exposed data only via APIs. This allowed teams to modify their database schemas independently without breaking other services.”
  1. CQRS (Command Query Responsibility Segregation)
  • What it is: Separating read operations (queries) from write operations (commands).
  • Why we use it: Complex reporting queries can slow down core transaction writes. CQRS uses one optimized model for updates and another optimized model for fast reads.
  • Interview Answer: “We used CQRS to separate heavy reporting from transactional writes. Writes went to our relational database, while read-optimized views were synced to Elasticsearch for fast searches.”
  1. Outbox Pattern
  • What it is: Saving database updates and Kafka events together in the same local database transaction.
  • Why we use it: Prevents event loss if your database update succeeds but your network fails right before sending the Kafka message.
  • Interview Answer: “We saved business data and the Kafka event into an Outbox table within the same database transaction. A background process published those outbox messages to Kafka reliably.”
  1. Distributed Caching (Redis)
  • What it is: Storing frequently accessed data in fast in-memory storage.
  • Why we use it: Reading from memory is much faster than querying a database every time. It cuts latency and reduces database CPU load.
  • Interview Answer: “We used Redis to cache frequently accessed metadata like campaign configurations and lookup tables. This reduced our database load and improved API response times.”
  1. Distributed Tracing & Centralized Logging
  • What it is: Assigning a single Trace ID to a user request as it flows across multiple microservices.
  • Why we use it: When an error occurs across 5 microservices, a single Trace ID lets you search central logs and instantly pinpoint which service failed.
  • Interview Answer: “We used centralized logging with correlation Trace IDs across Zipkin and Grafana. We could trace a single request across multiple services to quickly identify latency bottlenecks.”
  1. Scalability
  • What it is: Scaling microservices by adding more container instances as traffic grows.
  • Why we use it: Keeps your application responsive during high traffic spikes without needing a bigger single server.
  • Interview Answer: “Our microservices were stateless, allowing us to scale horizontally. During peak traffic, Kubernetes automatically added instances based on CPU usage and Kafka consumer lag.”

Core Spring Boot Topics

  1. Bean Lifecycle
  • What it is: The series of stages a Spring Bean goes through from creation to destruction.
  • Why we use it: It lets you run custom setup code (like loading cache data) right after dependencies are injected, and cleanup code (like closing DB connections) before the application stops.
  • Interview Answer: “The lifecycle follows: Instantiation → Dependency Injection → @PostConstruct → Ready state → @PreDestroy. I use @PostConstruct to pre-load configuration values or initialize connections right after the bean is created.”
  1. Spring Security
  • What it is: A framework that secures your application using a chain of security filters.
  • Why we use it: To authenticate users, check their roles (authorization), and protect endpoints from unauthorized access.
  • Interview Answer: “We used a stateless JWT-based Security Filter Chain. The filter intercepts incoming requests, extracts the JWT token from headers, verifies identity and user roles, and sets the security context for authorization.”
  1. Profiles (@Profile)
  • What it is: A way to segregate application configuration for different environments (Dev, QA, Prod).
  • Why we use it: Prevents hardcoding environment details so the same build can run across different servers seamlessly.
  • Interview Answer: “We separate environment configurations into application-dev.yml and application-prod.yml. By setting spring.profiles.active, the app dynamically loads the correct database URLs and log levels for that environment.”
  1. @Transactional
  • What it is: An annotation that manages database transactions automatically using Spring AOP proxies.
  • Why we use it: Guarantees that all database updates inside a method either succeed completely or roll back together if an error occurs.
  • Interview Answer: “Spring creates an AOP proxy around @Transactional methods to manage database commits and rollbacks. I keep transactions short, mark read-only methods with readOnly = true for performance, and rely on automatic rollbacks for RuntimeException.”
  1. Exception Handling
  • What it is: A centralized way to catch and format application errors globally.
  • Why we use it: Keeps controllers clean and ensures clients always receive clean, standard JSON error responses instead of technical stack traces.
  • Interview Answer: “We use @RestControllerAdvice and @ExceptionHandler to catch exceptions globally. It maps custom errors into a standardized JSON response with an error code and message, keeping internal stack traces hidden.”
  1. Validation
  • What it is: Annotations placed on Data Transfer Objects (DTOs) to enforce rules on incoming request data.
  • Why we use it: Rejects bad or malformed inputs at the API layer before they reach business logic.
  • Interview Answer: “We validate request body DTOs using @Valid along with Jakarta annotations like @NotNull, @Size, and @Pattern. If validation fails, Spring throws a MethodArgumentNotValidException which our global exception handler catches.”
  1. @Async and @Scheduled
  • What it is: @Async runs tasks in a separate thread. @Scheduled runs tasks automatically on a timed schedule.
  • Why we use it: @Async prevents blocking the main thread during long jobs (like sending emails). @Scheduled automates recurring jobs (like cleaning up old logs or polling outbox tables).
  • Interview Answer: “We use @Async with a custom thread pool for fire-and-forget tasks like email delivery. We use @Scheduled for background tasks like periodic Outbox polling and nightly data cleanups.”
  1. JPA Performance & N+1 Problem
  • What it is: A performance issue where querying 1 parent record causes Hibernate to execute N additional queries for child records.
  • Why we fix it: N+1 queries overwhelm the database and cause severe API slowness.
  • Interview Answer: “To avoid the N+1 problem, we use JOIN FETCH or @EntityGraph to load parent and child entities in a single query. For read-only APIs, we use Spring Data Projections to fetch only the required columns.”
  1. Performance Tuning
  • What it is: Optimizing database connections, memory management, and network delivery to speed up the app.
  • Why we use it: Reduces response times and handles high concurrent traffic using minimal server resources.
  • Interview Answer: “We tuned performance by configuring HikariCP connection pools, tuning G1GC memory allocation, caching static lookup data in Redis, and avoiding unnecessary database queries using JPA projections.”

What are REST and APIs?

API (Application Programming Interface): Think of an API like a waiter in a restaurant. You (the client) look at the menu, tell the waiter your order, the waiter goes to the kitchen (the server/database), and brings your food back. It is simply a way for two different software programs to talk to each other.

REST (Representational State Transfer): This is a set of rules or standard guidelines for building APIs so that system communication stays light, flexible, and simple across the web. An API built following these rules is called a RESTful API.

Database Performance and Optimization

“I optimize databases (Oracle and PostgreSQL) through five key steps:

  1. Smart Schema Design: Pick the right data types and normalize tables properly.
  2. Strategic Indexing: Index columns that are searched often, based on actual query habits.
  3. Query Fine-Tuning: Analyze query execution plans, run batch updates, and fix the N+1 select problem.
  4. Connection Management: Configure HikariCP connection pooling properly in Spring Boot so database connections are reused efficiently.
  5. Short Transactions: Keep database locks brief to avoid bottlenecks.

Using these methods, I achieved sub-200ms query response times under heavy loads at C-DAC and ensured high data accuracy at SBI Card.”

What is JWT Authentication?

“JWT (JSON Web Token) is a secure way to verify users without storing session data on the server:

  1. Login: The user logs in with a password. The server verifies it and gives back a encrypted digital badge (the JWT token).
  2. Requests: For every future request, the client attaches this token in the header.
  3. Validation: The server checks the token’s digital signature instantly—no database lookup needed.
  4. Expiration: Tokens expire automatically after a set time for security.

Why it’s great: Because it is stateless, it works perfectly across multiple microservices without requiring shared login session memory.”

Stateful vs. Stateless (and JWT)

  • Stateful: The server remembers you by saving your session in its memory or database.
    • Analogy: A local cafe where the barista remembers your face and order.
  • Stateless: The server does not remember you. Every request must carry all the proof needed to verify who you are.
    • Analogy: A vending machine—it doesn’t care who you are, it just checks if your coin/pass is valid right now.
  • JWT is Stateless: The token itself holds your user data and a digital signature. Any server can check the token’s signature on the spot without searching a database, making it perfect for scaling microservices.

16. Deployment, Routing, and Load Balancing Concepts

Blue-Green Deployment

  • Two environments run in parallel: Blue and Green
  • One version serves production traffic while the other is prepared for release
  • Once the new version is validated, traffic is switched over
  • Very useful for zero-downtime releases and fast rollback

Interview answer: “For critical banking and card platform releases, I prefer blue-green deployment because it reduces risk and makes rollback simple. We can validate the new version fully before moving traffic, which is important for high-availability systems.”

Canary Deployment

  • Release the new version to a small percentage of users first
  • Monitor error rate, latency, and business impact
  • Increase traffic gradually if the release is healthy
  • Good for controlled rollout and early risk detection

Rolling Deployment

  • Upgrade instances one by one instead of all at once
  • Keeps part of the system available during the process
  • Slower than blue-green but simpler to operate

API Gateway vs Load Balancer

API Gateway:

  • Handles routing, authentication, rate limiting, SSL termination, and request transformation
  • Best for application-level control and microservice access

Load Balancer:

  • Distributes incoming traffic across multiple instances
  • Focuses on availability and performance

Interview answer: “An API Gateway manages business-aware routing and policy enforcement, while a load balancer focuses on traffic distribution. In modern microservice systems, I use both together for security, resilience, and scalability.”

N4 vs N7 Load Balancing

N4 (Layer 4):

  • Works at the transport layer
  • Uses IP and port information
  • Faster and simpler
  • Good for general traffic distribution

N7 (Layer 7):

  • Works at the application layer
  • Understands HTTP path, headers, cookies, and request content
  • Better for API routing and service-specific rules
  • Commonly used by API gateways and smart load balancers

Interview answer: “N4 load balancing is simpler and faster because it works at the transport layer, while N7 is more intelligent because it understands application requests and can route based on API paths and headers.”

Load Balancing Algorithms

  • Round Robin: sends requests one by one to each server
  • Weighted Round Robin: gives more traffic to stronger or larger servers
  • Least Connections: sends traffic to the server with the fewest active connections
  • IP Hash: keeps the same client consistently mapped to the same server
  • Sticky Session: useful when session state is stored on a server

Interview answer: “The right algorithm depends on the workload. Round robin is simple and effective for even traffic, while least connections and IP hash are better when traffic patterns or session handling require more control.”

Health Checks and Failover

  • Health checks ensure only healthy instances receive traffic
  • Failed nodes are removed automatically from the pool
  • This improves availability and prevents routing to dead services

Deployment and Interview Notes

  • Use deployment strategy based on risk, downtime tolerance, and rollback needs
  • Always combine deployment with monitoring, health checks, and rollback planning

  • For banking and fintech systems, the key is not just deployment speed but safe, observable, and reversible release management
